## 0. The shape of the answer

Three claims organize everything below.

**Dependence comes from ownership, not instruction.** Your prior attempt failed on exactly this point: it asked the agent to follow procedures, and agents used them two times in five. An agent depends on a thing to the degree that the thing owns something the agent cannot route around. In an agent harness there are three such chokepoints, all of them ordinary code: **tool results** (where evidence physically enters), **context reconstruction** (what the agent receives at session start and after compaction), and **the answer slot** (what reaches the human). I propose to own those three and nothing else. Everything outside them is advice, and advice will be measured from outside, never relied upon.

**Your findings 8 and 9 resolve each other.** Your benchmark became fair by making every answer reconstructable from participant-visible data, and that made it solvable by plain careful reading. That equivalence — *visible implies solvable* — is a property of **short** contexts only. Across a long horizon a fact can be fully visible in the record and still lost, because it appeared forty thousand tokens or three sessions ago. Long-horizon instances are therefore the only known place where D4 (reconstructable) and D2 (headroom) can both hold. The instrument must be built there first — not because that is where the value probably is, but because it is where an honest test is possible at all.

**The instrument's credibility rests on a positive control.** You may never report a null from an instrument that has not first been shown to detect a known-good arm. That single rule is the auditable core of §2.

The bet in one line: **most reachable error in consequential agent work is context-loss error — a commitment made early, contradicted or invalidated later, with nothing in the loop that notices — and it is reachable by an external, append-only record that code checks on every write.** If the error census in Phase 0a says otherwise, the project stops in week two, having cost very little.

One governing discipline, stated up front because it is the specific way projects like this die: **the instrument obeys the same rules as the scaffold.** Anything I claim is computed must be recomputable (E1). Anything I claim about value must survive leave-one-out (E3). Anything that resolves must be logged where the thing being judged cannot rewrite it (B6). If the measurement apparatus gets to be sloppy while the scaffold is held to a standard, the project reproduces finding 7 by design rather than by accident.

## 1. The scaffold

### 1.1 What the user experiences

The user states a problem in their ordinary harness. Nothing changes unless a trigger fires. Most tasks never engage.

When one does fire, the agent works as it always has, but three things happen around it. Evidence entering from tools is recorded with its origin before the agent summarizes it. At the moment the agent moves to conclude, a fresh context that has never seen the draft is asked bounded questions about the recorded evidence. And the answer ships with a one-screen card generated by code from the record — not prose written by the agent about itself. The user can contest any input on that card and watch the conclusion recompute, with both verdicts kept.

The agent may gather. It may not conclude. Consequential answers are pure functions of a ledger the agent cannot rewrite.

### 1.2 Where it lives (E4)

Two integration surfaces, both harness-agnostic:

- **An egress proxy** on the model API. Every harness points at a base URL; the proxy sits there. It sees every call, every tool result, every token — from outside the agent. This is the external observation substrate (B4) and the compliance instrument (finding 3).
- **An MCP server** exposing ledger, contest, and render tools.

| Mode | Requires | What holds |
|---|---|---|
| **Full** | Proxy + MCP | Tool-result harvesting, enforced answer slot, verified isolation, external process receipts |
| **Partial** | MCP only | Ledger, origins, recompute, contest. Gate becomes annotation. No isolation claim. |
| **Advisory** | Neither | A file the agent is asked to write to. **No superiority claim is made in this mode, ever.** |

Reduced modes are named on every artifact they produce (`mode: partial`), so a reader never mistakes furniture for a keel. Before any building begins we need an honest inventory: which of your harnesses can wrap tools, and which can intercept the answer slot. If none can, we do not build a dependence claim — we say so and ship advisory mode labeled as advice.

### 1.3 The ledger — external, append-only, agent-writable but not agent-editable (B6, A6, A7)

```
Entry {
  id, session, ts, kind, content,
  origin: { source_kind, ref, content_hash },   // required
  depends_on: [id],                             // recorded at WRITE time (B5)
  entities: [str], quantities: [{val, unit}],
  status: live | suspect | retracted,
  retracts: id?                                 // retraction is a new entry, never a delete
}
```

Five kinds. The distinction between the first three *is* A6, and it is the load-bearing distinction in the whole design:

| Kind | Origin requirement | May carry a number? |
|---|---|---|
| `observation` | From outside the model. Origin = tool-call id + content hash of the raw result, or a human utterance id. | Yes |
| `computation` | Deterministic. Origin = expression + input entry ids. Recomputable by the ledger with no model in the loop (E1). | Yes |
| `elicitation` | The model's own judgment. Origin = prompt hash + call id. Permanently tagged. | **No** — never enters a computed figure |
| `prediction` | Claim + probability + **resolution criterion + resolution date**. Rejected without both. | — |
| `gap` | A named missing input. A first-class output, not a failure state. | — |

**Observations are harvested, not narrated.** The proxy extracts observation entries from raw tool results before the agent summarizes them. This is the single most important fidelity decision in the design: it removes the most consequential entry type from the agent's discretion, which is where finding 2 would otherwise eat the whole system.

**Why the agent writes the rest.** Not because it is told to. Because the ledger is the cheapest route back to its own context: at session start and after every compaction, the proxy injects a compiled ledger digest — entities, live commitments, open gaps, suspect entries, unresolved predictions — in place of a raw history dump. What was not written down is not in the digest. The notebook gets used because the notebook pays.

**Retraction cascade (B5).** `retract(id)` walks `depends_on` forward and marks descendants `suspect`. An entry written without dependency links is treated as depending on **every live entry in its session** — so a lazy write is flagged aggressively rather than silently exempted. That is the concrete meaning of "fails toward over-flagging," and the instrument scores what that bias costs (§2.2, Family L).

**Immutability is relative to the agent.** Hash-chaining detects corruption when checked against independently retained checkpoints; it does not stop a privileged operator from rewriting history. A local service account with separate credentials is sufficient for your context and does not require enterprise infrastructure. I will not overclaim it.

### 1.4 The collision check — the actual long-horizon intervention

Deterministic trigger; a model appears only at the last step:

```
on write(e) where e.kind in {commitment, computation, load-bearing elicitation}:
    candidates =  index.entity_overlap(e)
               ∪  index.same_dimension_quantities(e)
               ∪  ledger.suspect_touching(e.entities)
               ∪  ledger.constraints(scope ⊇ e.scope)
               ∪  ledger.predictions(unresolved, due < now)
    for c in rank(candidates)[:K]:                # K = 5, budget-scaled
        if seen(pair_hash(e, c)): continue
        v = cold_reader(pair=(e,c), facts=minimal_closure(e,c))   # 1 call, ≤4k tokens
        if v.conflict:
            write(observation{kind: collision, refs:[e,c], text: v.reason})
            mark_suspect(per v)
```

The retrieval corpus is the ledger — dozens to low hundreds of entries — not the transcript. That is why this is cheap and precise where full-transcript search is neither. The trigger is code; the agent cannot forget to run it, because it is not the agent running it.

The cold reader is a fresh context assembled by the scaffold from ledger entries. **The agent never passes text to it.** The proxy logs the exact prompt, so a third party can verify by hash that the draft and the lean were absent (B1 — observable from outside the component claiming it).

### 1.5 Counterparts, and what a fresh context actually buys (B1–B3)

A counterpart is either a **tool** (computes) or a **fresh context** (judges). It is never a role-play in the working window. Self-critique, debate, and personas rearrange what is already there; by your own §2 that is not evidence, and it costs what finding 10 costs.

**Packs.** The runtime builds the counterpart's context in code from the question plus `observation` and `computation` entries. Truncation, if any, is recorded as part of the pack — silent omission is not representable. Entries the agent proposed but that were not included appear on the card as a contestable fact.

**Isolation proof.** The runtime writes `{context_hash, included_ids, excluded_types, model_id, seed}`. A judgment without a runtime-authored proof is not an input to any computation. The agent cannot author the proof because it does not author the context.

**Competence is never traded for independence (B3).** Every counterpart sees the whole pack. Finding 10 is a standing rule here: atomizing evidence to one item per judge destroyed each judge's view and cost 87 calls for three instances. Independence is bought from blindness to the draft and from varied framing — never from fragmenting the evidence. If a split is ever used, the competence cost is measured by scoring split judges against whole-view judges on the same items, and stated.

**What a same-model fresh context honestly provides:** exposure independence (it did not see the draft), no commitment to a prior answer, and additional hypothesis coverage. It does **not** provide an independent witness about the world. Three distinct things get conflated under "independence," and this design keeps them apart:

| | What it means | How it is established |
|---|---|---|
| **Exposure independence** | The judge did not see the draft, the lean, or other judgments | Runtime-authored isolation proof; verifiable by hash |
| **Error independence** | The judge fails on different cases | Measured offline on resolved items (§2.4); unmeasured = none |
| **Lineage independence** | Different training causes of error | Usually unknown; **never claimed** |

Any output that aggregates reports `n_eff = n / (1 + (n−1)ρ)` using the **conservative upper bound** on measured ρ. Unmeasured correlation means ρ = 1, so five judges report as one. Sample count is never displayed as corroboration.

**Start with one counterpart.** The agent gathers; one isolated judge sees the whole problem; code combines. A second judge is an experiment that must survive leave-one-out. Ten judges are refused.

### 1.6 Combination is code (E1, and the direct fix for finding 6)

There is no chairperson and no strength-weighted argumentation calculus. Your finding 6 — the verdict collapsing exactly to the model's prior whenever the sides arrived equally strong, mathematically correct and decorative — is a property of any aggregator with a prior slot. I will not rebuild it under a new name.

Provisional rules, frozen before collection:

- **Diagnosis / competing stories.** The hypothesis set is frozen in the question or written as `observation`/`elicitation` entries before judging. Combination eliminates hypotheses contradicted by registered observations and reports what survives. If more than one survives, the answer is *"not determined among {…}"* plus the observation that would most reduce the surviving set — computed by counting, not judged. **A tie never resolves to a prior.**
- **Estimation.** An explicit formula over inputs each carrying a recorded range from its source. A judge's number enters only if it cites pack ids for every input; otherwise it is `elicitation` and is dropped from the numeric aggregate. Interval = judge spread, labeled *judge spread*, not a calibrated CI, unless an unexpired calibration says otherwise.
- **Claim-support.** The load-bearing object is a claim list, each claim linked to observations. A blind judge marks each `supported | unsupported | overclaimed`. That marked list is the answer; prose is commentary generated afterward and cannot add a claim.

**Standing regression test.** Before any aggregator ships, and again on every model change, it is run against synthetic cases where both sides are equally strong, with the model's raw prior elicited separately. If the aggregated verdict correlates with the prior above a pre-registered threshold, the aggregator is rejected — not patched. At runtime, any aggregation also runs a **prior-only control**: judges with evidence stripped. If the verdict falls within ε of the prior-only verdict, the output does not print a verdict. It prints: *"this verdict is not distinguishable from the model's prior; the following evidence would separate them."* Your decorative-verdict class becomes a refusal.

### 1.7 The gate and the renderer (A2, A3, A4, A7, A8, C5)

The deliverable is composed by code. The agent supplies narrative and references; the renderer validates and assembles.

1. Load-bearing claims must reference ledger ids. No reference → rendered as a **visible hole** naming the unsupported claim.
2. The origin chain must terminate in `observation` or `computation`; otherwise the claim is tagged `ELICITED` inline and excluded from every computed figure.
3. Any `suspect` ancestor → hole: *"rests on retracted input #47 (retracted 2026-09-02, reason: …)."*
4. Relabelling an entry's kind to clear a stop is itself a ledger entry and appears on the card (A7's visibility clause). Only a human may relabel.

**It never blocks.** Holes render, the answer ships with holes visible, and one optional repair round-trip happens if budget allows. A counterpart that can wedge the thinker is worse than one that is absent (C5), so the gate degrades to annotation, always. The only thing that halts is a *claim of computation* over a missing origin — and the agent remains free to answer in prose, clearly marked as prose.

**Sensitivity, computed rather than asserted (A3, A4).** Where a computation graph exists: recompute with each input removed, negated, or at its stated bounds; rank by |Δ|. Where the conclusion is qualitative: ablate — re-run the final synthesis N times (N=5 default) with each high-centrality entry removed, and record flips. Every sensitivity table carries the same footer: *"Exact over recorded inputs only. One-at-a-time; joint dependencies not searched. Entries not in the ledger were not tested."*

That footer is not decoration. **Universal exact answer-sensitivity for arbitrary prose reasoning does not exist**, and inventing numeric weights to make it look exact would be the first shape in your §7. Where a genuine decision rule exists, the sensitivity is exact and I will say so; where it does not, the card reports an incomplete decision specification and a bounded dependency analysis, and says which it is giving you. During development we compare one-at-a-time flips against a cheap sample of pairwise flips; if they disagree often, the footer gets stronger or we pay to search joints. We do not ship the prettier ranking silently.

**Contest (A8).** `contest(entry_id, replacement, who, why)` appends a new entry, recomputes deterministically, and emits both verdicts side by side, permanently. Gaming an input is possible and permanently visible — which is the point, and which is what fixed two of your four wrong verdicts by hand.

### 1.8 Score-keeping

A `prediction` entry requires a resolution criterion and date or the API rejects it. Resolution is written by the operator or by an authorized tool result — never by the predictor (B6). Calibration tables carry the model version and date range they cover and **stop being emitted** when the version changes or the sample ages past a pre-registered window (E2). A stale basis cannot keep a live badge. Self-graded history is refused outright.

### 1.9 The watcher (B4, §8 Q3)

The proxy answers the compliance question without ever asking the agent:

- **Trace correspondence.** Every process artifact must have a matching call trace. A sensitivity table with no corresponding ablation calls in the proxy log was typed, not computed — forged, detected.
- **Recompute-and-diff.** On a randomly sampled fraction of *ordinary* runs (sampling lives in the proxy, invisible to the agent), re-derive the artifact from the ledger and diff. Non-reproducible → forgery event, logged.
- **Uptake.** Ledger writes per task, digest-read rate, gate-hole rate — all from outside. This is the only compliance number that will ever be reported, and it comes from ordinary use, never from a run where the procedure was ordered (finding 2's lesson about the meaningless 100%).

What a receipt proves is stated narrowly and will not be inflated: that a request was dispatched, with specified context, returning a specified output, at a recorded cost. It does not prove the model internally considered alternatives sincerely. A forged agent-authored table cannot satisfy a receipt; a real call producing a shallow judgment still can. The first is an enforcement problem, solved here. The second is an outcome-quality problem, measured by the instrument. That distinction is not negotiable.

### 1.10 Engagement, interruption, and the human surface (C1–C5)

**Engagement is code over explicit triggers**, not a learned policy — there is no outcome data to learn from, and pretending otherwise is the §7 shape "a learned selection policy with no outcome data." Triggers: the task spans more than one session or exceeds N tool calls; a number will be asserted in a deliverable; a retraction fired; the user flagged the decision irreversible; a ledger already exists for this task. **Default is silence**, and the decline rate is reported every run (C4). Uncertain → decline, never halt (C5). The user never sees a menu of techniques (C2).

**Interrupts (C3)** fire for exactly four things: a value judgment, a materially ambiguous meaning, evidence only the human holds, authority over an irreversible act. And they *do* fire for those. Critically, ambiguity and value-sensitivity are **computed before interrupting** — if all plausible readings lead to the same answer, the human is not asked. So the question is never *"which technique do you want?"* It is: *"If reversibility outranks immediate cost, option A is robust; if not, option B. Which governs here?"* Every gate has a timeout and fails open, visibly.

**The card (C1)** is one screen, generated by code:

```
ANSWER      Not determinable: H1 and H2 both remain compatible.
MODE        full   COST  $0.41 · 5 calls · 47k tokens · ceiling $0.60 · degraded: no
RESTS ON    1. [#12 obs] Error began before deploy A completed    flip → H3 viable
            2. [#19 obs] Both H1,H2 predict the observed retries
            3. [#23 gap] Lock telemetry 13:58–14:06 unavailable
CHANGES IF  lock telemetry present → H2 confirmed
            start time after 14:08 → deploy A becomes plausible
UNKNOWN     DB lock state in the 8-minute window
ORIGINS     observation 7 · computation 3 · elicitation 5
INDEPENDENCE isolated: yes · judges: 1 · n_eff: 1.0 (correlation unmeasured)
STABILITY   held under reorder + rename · 1 hypothesis appeared only in blind view
CONTESTS    none
            [contest an input]  [view ledger]  [full cost]
```

No technique names. No "we deliberated." Ranked supports appear only if the code produced the ranking.

**C1 is a release gate, not an aspiration.** Five readers who have read no documentation answer five factual questions about a run in under two minutes with ≥80% accuracy. Fails → the card is redesigned before anything else ships. Finding 11 is a product defect and gets a product gate. The same discipline applies to the project itself: a weekly one-page state report, in the card's own format — what ran, what it cost, what we now believe, what would change it, what is unknown — starting week 1, before there is a scaffold to describe.

**Cost (B7).** Every engaged act runs under a stated ceiling. When it binds, degradation follows a fixed published order — independence sampling → sensitivity N → collision K → collision checks on low-centrality entries — and the card reports what was skipped and what it actually cost. Never silent.

## 2. How we measure before we build, and what would make us stop

**No scaffold component beyond a thin logger is built until the instrument passes its own validation.** The instrument is a separate deliverable in a separate repository with a separate owner, because a benchmark authored by the person building the component it tests is how finding 7 happens four times.

### 2.1 Phase 0a — Error census on your real corpus (weeks 1–2)

Before families, before headroom, before anything: sample ~100 failures from your corpus of real consequential tasks with known outcomes. Two raters code each independently against a fixed taxonomy; report Cohen's κ; the domain reviewer adjudicates.

| Class | Definition | Reachable by this design? |
|---|---|---|
| **E1 Evidence-absent** | The fact was never available to the agent | No — better tooling only |
| **E2 Context-loss** | The fact was available earlier and was lost, contradicted, or silently superseded | **Yes — the target** |
| **E3 In-context slip** | Everything needed was in one window and the agent still erred | Partly — gate catches unsupported numbers |
| **E4 Capability ceiling** | The model cannot do the reasoning at any horizon | No |
| **E5 Specification** | The wrong question was answered | Partly — C3 interrupts |

**Kill criterion:** if E2 plus the gate-reachable part of E3 is under **15%** *(provisional; fixed in writing before coding begins)* of coded failures, stop. Recommend at most a ledger-digest memory tool, and report the number.

This is the cheapest decision-relevant measurement available, it is the direct answer to §8 question 1, and it costs about two person-weeks. Your prior attempt spent a serious effort without ever establishing that the target error class exists at a rate worth addressing.

**Phase 0b, run in parallel — does reset do anything?** Three arms on a development slice, no scaffold required: *Seen* (model gets sources plus a prior draft, then concludes), *Blind* (fresh context, sources only, same budget), *Unaided* (ordinary pass). If *Blind* does not beat *Seen*, isolation is not buying a second opinion and the counterpart layer is not built. This also yields the first error-correlation numbers that §2.4 will later cite.

**Phase 0c, also in parallel — is ceremony already a harm?** Take unaided outputs and render them two ways: plain prose, and a mock structured card whose content is identical. Show both to readers who must act. If structure raises confidence more than accuracy, D10 is a live defect of the *display* before a scaffold exists, and the card in §1.10 is designed against that finding rather than discovering it after we are invested in our own tables.

### 2.2 Phase 0d — Task families with demonstrated headroom (weeks 2–6)

Four families. Each instance is a multi-session task, not a prompt.

**Family L — long-horizon collision** (primary; D8). Structure: a **commitment point** early — a constraint, a ruling-out, a stated quantity, established from a tool result or stakeholder statement; then **drift** — 20–60 steps of legitimate work that never mentions it; then a **collision or retraction** — a later observation invalidates the commitment, or a required decision contradicts it; then a **scored probe**.

Scored fields, each designed against a constant strategy (D3):

- **Contradiction** (binary). The pool contains both polarities in an undisclosed ratio, so "always contradicts" and "never contradicts" both lose.
- **Invalidation set** (set-valued): which earlier conclusions must now be flagged. Distractor conclusions that do *not* depend on the retracted premise are included, so "flag everything" loses. **Misses and over-flags are scored and reported separately, never combined into an F1.** B5 deliberately biases the mechanism toward over-flagging; the metric must show what that costs.
- **Quantity** (numeric, banded), where the correct value requires the early constraint.
- **Determinability**: a pre-registered fraction of instances are genuinely non-determinable. Correct answer = refuse *and name the specific missing input*. Always-refuse loses; always-answer loses. This is the direct test of A2.

**Family R — messy real tasks** (D9). Drawn from your corpus, outcomes known. The scaffold builds its own representation. **Representation faithfulness is scored separately from outcome correctness**: the domain reviewer marks the facts that were actually load-bearing for the known outcome, and we score the ledger's recall and precision against that set. A scaffold with 40% recall of load-bearing facts is capped no matter how good its machinery is, and this field says so directly.

Where outcomes are known only in hindsight, the answer key is the *justified decision given evidence available at the time*, not the eventual outcome. A known outcome is not automatically a fair key.

**Family P — perturbation** (A5). Each instance in 4–6 information-free variants: reordered evidence, renamed entities, rephrased stakeholder confidence ("fairly sure" → "about 70%"), reformatting. Finding 5 — conclusions flipping 3/3 on rephrased confidence — becomes a number with a denominator.

**Family S — sealed** (D5). Same construction, never inspected by anyone touching the scaffold, scored once at the end, reported separately.

**Headroom validation (D2), before any scaffold exists:** run 3–5 unaided baselines — different models, different harnesses, generous budget — on every instance. Retain the family only if the baseline failure rate lands in **30–85%** *(provisional band)*. Outside it, revise or discard; a family surviving two revision rounds without landing in the band is discarded, **and the discard is reported**. This is the check that would have caught findings 8 and 9 before they cost you ten runs of byte-identical answers.

**Kill criterion:** if no family reaches the band after two iterations, stop. "Consequential-task headroom could not be constructed honestly" is itself a publishable finding about the problem.

### 2.3 Phase 0e — Instrument integrity (weeks 4–7)

Each of your four instrument breaks gets a standing automated detector, run on every instance before it enters a pool:

| Your failure | Standing detector |
|---|---|
| Answer key contradicted its method | **Independent reconstruction (D4):** a second party derives the scored answer from participant-visible data only, without the key. Mismatch → instance rejected. Reconstruction logged. |
| Costs leaked the hidden answer | **Blind statistician:** a model sees only metadata — token counts, tool-call counts, timing, file sizes, structure — and predicts the answer. Above chance → instance leaks → rejected. |
| Scorer accepted only one valid answer | **Variant sweep:** the reconstructor produces *all* defensible answers; the scorer must accept the full set. Any answer a human adjudicator calls correct that the scorer rejects is a tracked scorer-bug rate. |
| Control arm found the procedures on disk | **Sandbox manifest diff:** control directories hashed before and after; any path in the scaffold namespace present at start voids the run. Control arms run from a separate container image. |

Plus **mutation tests** on every scorer — plant one defect at a time (wrong number, unsupported number, stale premise, omitted contradiction, valid-but-unexpected phrasing) and confirm the scorer catches what it claims to catch and accepts valid equivalents — and a **clueless baseline** given only structure and no content. Any family where it beats chance has structural leakage.

**Kill criterion:** instance rejection above 50% after detector tuning means the generator is unsound. Rebuild or discard.

### 2.4 Phase 0f — Arms, power, pre-registration (weeks 7–8)

Five arms. All run under **identical token and wall-clock budgets**; the baseline may spend its budget however it likes, including extra sampling, self-critique, and longer thinking. A win bought with 5× the tokens is not a win.

| Arm | What it is | What it tests |
|---|---|---|
| **Unaided** | The agent, plain, matched budget | A1's denominator |
| **Strong-memory baseline** | Harness-native memory and compaction plus a plain "keep notes as you go" instruction | The most likely null: that the harness already does most of this |
| **Sham** | Identical ceremony, same structured card, same token spend, mechanisms disabled — ledger ordering randomized, cold readers shown the draft, gate validating nothing | Whether any effect is mechanism or ceremony (findings 6 and 7; D10) |
| **Scaffold** | The real thing | The hypothesis |
| **Oracle-fed** | The scaffold with its ledger pre-populated by the key's load-bearing facts | **Instrument sensitivity** — see §3 |

**Paired design.** Every instance runs under every arm; analysis is within-instance difference. This cuts variance enormously against a between-subject design and is the main reason the study is affordable. Three seeds per cell to estimate run-to-run variance.

**Power before data.** A 20-instance pilot on Family L, Unaided vs. Sham only, estimates σ of the paired difference. From that we compute the minimum detectable effect at candidate n. **Futility rule, pre-registered: if the MDE at the affordable n exceeds the effect you would act on, we do not run the study** — we buy more instances or stop. Running underpowered is precisely how you arrived at "we still cannot say whether any of it works."

The effect you would act on is yours to name, not mine; it should come from expected error cost against scaffold operating cost. My provisional proposal for Family L is **10 percentage points absolute** on the composite score. Fix it before the pilot.

For rough planning: with 800 paired instances and a paired disagreement rate of ~0.25, SE(Δ̂) ≈ 1.8 points, giving a ~±3.5-point interval near zero — enough to exclude a 10-point gain. Clustering across task variants from the same source will inflate this; variants never count as independent instances.

**Pre-registration (D6)** is signed and hashed before collection: metrics, arms, n, exclusions, stopping rules, analysis code committed. Results report **both directions** as a matched pair of counts — instances fixed and instances broken — never a net.

**Rerunnability (D7):** container image + instance bundle + seed. `make results` reproduces every number in the report from frozen artifacts. Replaying live model calls is a separate capability and is *not* promised to be identical.

## 3. How our own null result gets detected, and how you audit the detector

The failure you most need protection against is not "the scaffold doesn't help." It is "the instrument couldn't have told us either way."

**3.1 The positive-control doctrine.** The oracle-fed arm has the ledger pre-loaded with exactly the facts the key says are load-bearing. Everything downstream runs normally. This arm *should* win by a wide margin. If it does not, either the instrument cannot detect improvement or the downstream mechanisms cannot exploit correct inputs.

> **Standing rule: the instrument may not report a null unless, in the same run, the oracle arm beat the unaided arm on the primary metric at p < 0.01.** A null from an instrument that failed its positive control is voided and the instrument is repaired.

You audit this by reading one line in the results table. It is deliberately hard to fudge: the oracle arm shares all code with the scaffold arm and differs only in a ledger seed file you can inspect.

**3.2 The sham arm bounds ceremony.** If Scaffold ≈ Sham, the effect is presentation, not mechanism, and the honest report is "no mechanism effect detected." This makes finding 6 a study-level result rather than something discovered by accident in one trial.

**3.3 The verdict is not "p > 0.05."** Failing to reject zero is not a null result. Before the confirmatory study, with δ fixed, a deterministic script reads the pre-registered result file and emits exactly one verdict:

| Verdict | Condition |
|---|---|
| **Worth advancing** | Estimate reaches δ, interval excludes zero, trust and safety guardrails pass |
| **Practically unhelpful** | Upper confidence bound below δ |
| **Practically equivalent** | Entire interval inside the pre-registered equivalence band [−δ, +δ] |
| **Harmful** | Interval supports increased error, or the severe-breakage guardrail is crossed |
| **Inconclusive** | None of the above — permits only a pre-registered extension under a fixed ceiling |

The "harmful" verdict fires **independently of the average**, because your §3 anti-goal is about the worst case, not the mean.

**3.4 The detector is itself tested.** Before it judges anything real, `measure.py` is run against synthetic bundles with a planted +δ, a planted 0, a planted −δ, and a ceremony-only difference. If it does not recover the planted signs, no claim is issued.

**3.5 A null is the deliverable.** The Phase 1 report is written to be publishable whichever way it comes out. "Long-horizon scaffolding does not improve consequential agent work at matched cost, effect 0.02 ± 0.06" is the project's output and is worth what it cost. There is no supplementary qualitative channel that can overturn the table; qualitative notes may explain *where* it broke, never reverse the verdict.

**3.6 Trust is measured as discrimination, not confidence (D10).** Readers see a mix of correct and incorrect outputs from each arm and rate probability-correct. The metric is **reader-judgment AUC per arm** — can readers tell right answers from wrong ones? If the scaffold raises confidence on *wrong* answers more than baseline does, the offending presentation feature is removed within one iteration, or the card ships stripped. Not a caveat. A gate.

## 4. What I refuse to build

1. **Self-critique, debate, personas, or multi-sample ensembles presented as corroboration.** They reorganize what is already there. Permitted only as `elicitation`, tagged, never aggregated into a computed figure, never counted as witnesses.
2. **Any compliance or process metric derived from the agent's own report**, including self-authored analysis tables presented as evidence that analysis occurred. Compliance comes from the proxy or does not exist.
3. **Strength-weighted argumentation or any aggregator with a prior slot** that cannot pass the tie-collapse regression test of §1.6. Finding 6 in mechanism form.
4. **Atomized judges.** One evidence item per judge destroys competence and costs what your 87 calls cost. Independent nonsense does not average into sense.
5. **Unresolvable confidence numbers.** A prediction without a resolution criterion and date is rejected at the API. No probability reaches a deliverable unless it resolves or comes from an unexpired calibration set.
6. **Calibration or coverage claims without enforced expiry.** Model-version and date fingerprints; the renderer refuses to print an expired claim.
7. **A learned engagement or technique-selection policy** before there is resolved outcome data to learn from. Rules and default-decline until then.
8. **Anything that can wedge the agent's ordinary work.** The gate annotates; it never halts.
9. **Exact sensitivity claims for unconstrained prose reasoning.** Where no defensible decision rule exists, the card says so rather than manufacturing weights.
10. **A user-facing catalog of techniques.** If the value depends on the user knowing the vocabulary, the design has failed.
11. **Any claim more general than two forms:** *this computation is exact over these recorded inputs*, and *this measured difference, at matched cost, with this uncertainty, for this family, under this model version*.
12. **A superiority claim in advisory mode**, where the harness cannot intercept anything.
13. **Any benchmark instance authored by the person or process building the component it tests.**
14. **Training or "improving unaided thinking" as a goal.** Weights do not change. We may measure transfer once; we will not build for it.

If a later idea needs one of these to look good, the idea is rejected, not the list.

## 5. What it costs

Dollar figures depend on your model pricing, which I will not invent. Here is the cost model in tokens; multiply by your rates.

**Per consequential task**, baseline = B tokens; assume a three-session diagnosis at B ≈ 400k:

| Component | Cost | Notes |
|---|---|---|
| Ledger writes | +3–8% of B | Piggybacked on calls already being made; harvested observations cost nothing extra |
| Digest injection | −5% to +5% | Often *cheaper* than raw-history compaction |
| Collision checks | 10–30 calls × 3–4k ≈ 40–120k | The dominant new cost; bounded by K and budget |
| One blind counterpart | ~1 whole-pack pass | Only on full-mode consequential renders |
| Render + gate | 1–3 calls + code | Small |
| Sensitivity ablation | N=5 re-runs ≈ 30–80k | Only on consequential renders |

**Provisional target: total overhead ≤ 40% of baseline task cost**, hard-metered, with the published degradation order in §1.10. Declined tasks cost one cheap routing classification. If a prototype exceeds ~2× without a matching primary-metric gain, leave-one-out removes the expensive part.

**Measurement cost — the larger number, and the one your prior attempt underestimated by an order of magnitude:**

- Pilot (20 instances × 2 arms × 3 seeds = 120 runs): ~50M tokens plus instrument engineering.
- Main study, provisional: 60 instances × 3 families × 5 arms × 3 seeds ≈ **2,700 runs**; at ~400k tokens/run ≈ **1.1B tokens**. Paired analysis is what makes 60 instances per family sufficient; a between-subject design would need several times this.
- Sealed family: +540 runs.
- Reader study: 30–40 readers × ~12 items, plus recruitment and analysis.
- **Instance construction and D4 reconstruction is the real bottleneck**: roughly 3–6 hours of combined authoring and reviewer time per Family L instance. 180 instances is ~4 person-months. This dominates the schedule and likely the budget, and should be attacked with semi-automated generation from real traces plus human validation — not hand-authoring.

Authorize only the first tranche now: the error census and instrument qualification. Revise every later estimate from observed runtime and reviewer throughput. The futility rule exists precisely so we discover an unaffordable MDE *before* spending the rest.

## 6. The strongest case against this design

**6.1 The harness already does it.** Modern harnesses have memory and compaction. If native compaction plus "keep notes as you go" captures most of what the ledger captures, the marginal effect is near zero and everything above is overhead. *This is the most likely null and the cheapest to find.* The strong-memory baseline runs in the **pilot**, before the scaffold exists. If it closes more than ~70% of the oracle-to-unaided gap, stop.

**6.2 Ledger fidelity caps everything — the representation bottleneck.** This is the deepest objection and it deserves a plain statement: the deterministic parts are exact only about the case graph they receive. If the model omits the decisive observation, misreads a source, records a false dependency, or never generates the right hypothesis, the runtime produces a stable, reproducible, well-provenanced answer that is still wrong — and its structure may make that wrong answer *more* persuasive. The ledger solves forgetting better than it solves misunderstanding.

Harvesting observations from raw tool results removes the worst of this, since the most consequential entry type never passes through the agent's discretion. Commitments and constraints remain agent-authored. *Detection:* Family R's representation-faithfulness score, measured **before** the main study. Provisional gate: **load-bearing-fact recall below 70% means the mechanism cannot work and we say so rather than tuning around it.** A development-only diagnostic — run with a reviewer-corrected representation — tells us whether representation construction rather than memory is the bottleneck. That diagnostic never counts as product performance.

**6.3 Collision-check precision.** A check that fires on every unit-matched quantity is noise: it burns budget and trains everyone to ignore it. *Detection:* fire rate and precision measured on Family L in the pilot. Provisional gate: precision ≥ 0.5 at a fire rate ≤ 1 per 10 ledger writes, or the trigger is re-specified before the main study.

**6.4 Over-flagging becomes unusable.** B5's conservative cascade could produce so many suspect flags on long tasks that a human stops reading them — the classic alert-fatigue collapse. *Detection:* the separate over-flag metric in Family L, plus the operator's own tolerance in the two-minute card test. If the card gets ignored because it is noisy, that is measured, not assumed away.

**6.5 The agent routes around the gate.** It writes the answer in chat. The proxy sees this, so it is measured rather than assumed — but in partial mode it is unfixable, and partial mode is where some of your harnesses will live. Field observation of what people actually treat as the answer is the alarm.

**6.6 Trust inflation.** The card is exactly the kind of artifact that raises reader confidence faster than accuracy. Phase 0c measures this before we are invested; §3.6 gates it before release.

**6.7 Maintenance across harnesses.** Three harnesses, a proxy, an MCP server, and an evaluation rig is a real ongoing burden for a small team. The proxy being the sole integration point is the mitigation; if it is not enough, the honest move is to support one harness properly and document the rest as unsupported.

**The failure I would bet on if forced:** 6.2 and 6.5 together — a correct constructor that the agent walks around in a harness that lets it, producing structured commentary that inflates trust without touching the error. That combination is worse than nothing. It is why the answer slot is a chokepoint rather than a convention, why advisory mode carries no claim, and why the trust gate is a gate.

**The cheapest way this project succeeds** is by discovering that only the append-only ledger with automatic invalidation is worth keeping. The measurement is deliberately built so that conclusion can emerge, and it would be a good outcome.
