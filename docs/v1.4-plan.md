# v1.4 plan — measure first, on a model that can fail

Status: **P0 done; P2 wave 1 finished with seven pre-registered results** (2026-09-16). On one abstention task, ordering a model to use the v1.3 controller beats spend-matched baselines: +10.4 pts over a higher-effort baseline for Haiku 4.5 (CI +3.1 to +18.8, n=96) and +33.3 for Gemini 3.5 Flash Lite (CI +18.8 to +47.9, n=48). Skills left merely available are not used (Haiku 0 of 200). Opus 5 scores 94% unaided on this family, so it is ceiling-limited and every Opus verdict is void — the frontier is still untested. Spend: Anthropic $67.89, OpenRouter $23.25. Branch `v1.4`,
cut from the v1.3 commit `4307690`.

Sources: [`design-brief.md`](design-brief.md) is the problem, and
[`v1.4-design-response.md`](v1.4-design-response.md) is a design answer to it (cited here
as **R§n**). This plan turns that answer into work this project can actually do. It
keeps most of the answer, changes the parts that clash with this repo or can't be done
here, and adds one thing the answer lacks: a **weak subject model**.

---

## 1. What v1.4 is

- v1.3 shipped eighteen recipes and seven aggregators. **We still cannot say whether any
  of them help.** Every test we ran either had a broken instrument or no headroom.
- The frontier model solved our planted traps by careful reading alone (brief §4,
  findings 8 and 9). A test the unaided model already passes can't show whether the
  scaffold does real work or is just ritual.
- So v1.4 runs its experiments on **Claude Haiku 4.5** (`claude-haiku-4-5-20251001`), a
  model that can still fail, and then checks whatever it finds against Sonnet 5 and
  Opus 5.
- v1.4 builds the **instrument first**. Scaffold pieces get built only after a gate says
  the instrument can see an effect.
- The bet it tests is from R§0: most reachable error is **context loss over a long
  horizon**. An append-only record, checked by code on every write, can catch it.
- **A null result is a valid end.** "It doesn't help Haiku, and here is the number" counts
  as a finished v1.4.

---

## 2. Why Haiku, and the rules that keep it honest

**Why:** headroom and cost. A family where the unaided subject fails 30–85% of instances
(R§2.2, D2) is easy to build for Haiku and nearly impossible for Opus. Haiku runs are also
cheap enough to afford the sample size that the power calculation demands (§5, P4).

**The risk:** a weak model changes *what* is being measured. Five rules handle that.

| # | Rule | Why |
|---|---|---|
| H1 | **Same model everywhere inside an arm.** Fresh subagents, cold readers and counterparts in a Haiku arm are Haiku too. | If Opus reads for Haiku, a gain means "a better model helped". That is model routing, not scaffolding. A stronger-counterpart arm may be run, but it is reported on its own line. |
| H2 | **Model ladder on every family.** Run the unaided baseline on Haiku 4.5, Sonnet 5 and Opus 5. | Picks the subject tier by headroom rather than by assumption. How the gain changes with model strength is the ritual test for frontier models (§7). |
| H3 | **Separate "can't run it" from "doesn't help".** Every study has a *skills-ordered* arm, an *oracle-fed* arm, and uptake counted from traces. | Haiku may fail to operate an 18-recipe controller at all. Without these arms, "the scaffold is useless" and "Haiku can't use it" look identical. |
| H4 | **Pin the model id in every run record.** Results expire when the model changes (E2). | A Haiku number is a claim about that Haiku build. |
| H5 | **A Haiku gain licenses a Haiku claim only.** No general claim ships before the frontier check in P6, run on the same instances. | Compensating for a weak model is useful, but it is a different product from helping a strong one. |

**Changed:**

## 5. Phases and gates

Weeks assume one person, part-time model budget, and no reader pool.

### P0 — Clean-room runner (week 1)

Build in `bench/`:

- **`run_arm`**: one run = one fresh temporary working directory outside the repo,
  `--model <pinned id>`, pinned effort, `--output-format stream-json --verbose`,
  `--max-budget-usd`, `--strict-mcp-config` (with `--mcp-config` only in arms that get the
  server), `--disable-slash-commands` in arms without skills, `--setting-sources project`
  so your user-level settings, skills and MCP servers don't leak in,
  `--disallowed-tools WebSearch WebFetch` in **every** arm (public datasets have their gold
  answers online), stdin from `/dev/null`. `--bare` where the arm needs no hooks (it skips
  hooks, CLAUDE.md discovery and auto-memory, and needs API-key auth).
- **Trace parser**: from `stream-json`, count tool calls, Skill invocations, subagent
  spawns, MCP tool calls, tokens and cost. This is the **uptake instrument**. It reads
  what the harness recorded, never what the agent says it did.
- **Contamination checks**: the init event of every control run must list no skills, no
  MCP servers and no user memory. The sandbox manifest is hashed before and after
  (R§2.3). A scaffold-namespace path present at start voids the run.
- **Hook payload check**: confirm that `PostToolUse` receives the raw tool output, that
  `SessionStart` fires on `compact`/`resume` and can inject context, and what `Stop`
  receives. Write the findings down; P5 depends on them.

**Gate G0:** ten control runs come up clean on every check, and the parser matches a hand
count on three transcripts.

**First probe (2026-09-15)**, one Haiku run with `--setting-sources project
--strict-mcp-config --disable-slash-commands --no-session-persistence`:

| Check | Result |
|---|---|
| skills / MCP servers / slash commands / plugins in init event | all empty — isolation holds for these |
| auth | subscription (`apiKeySource: none`) |
| fixed overhead per run | ~23.5k input tokens (harness system prompt, mostly cached) |
| cost of a trivial run | $0.015 at list price (`costBasis: list`) |
| **leak: auto-memory** | on by default — `memory_paths.auto` points at a new `~/.claude/projects/<sandbox>` dir per run. **Fixed:** `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` removes it (init shows `memory_paths: None`). |
| **leak: web tools** | `WebSearch` and `WebFetch` present by default. **Fixed:** `--disallowed-tools WebSearch WebFetch` removes both from the init tool list. |
| **drift: thinking** | on by default (262 thinking tokens on a one-word task) — pin effort per arm |
| user-level CLAUDE.md | **Canary check passes.** Asked whether three phrases unique to your global instructions appear in context: all `false` under `--setting-sources project`, all `true` under `--setting-sources user`. The check can tell the two apart, so the negative means something. |

### P1 — Headroom on the existing bench, and a first number for v1.3 (weeks 1–3)

1. **Ladder.** Unaided Haiku, Sonnet and Opus, 30 seeds each, one run per seed, scored by
   `score_instance.py`. Report the failure rate per scored field and per tier.
   - **G1a:** some tier fails 30–85% of instances on the composite. If even Haiku fails
     under 30%, this bench has no headroom for any tier: record that and move all effort
     to P3. If Haiku fails over 85%, move up to Sonnet as the subject.
2. **Arms on the chosen tier** (Haiku expected): *unaided*, *v1.3-available*,
   *v1.3-ordered*, and *oracle-fed* (the brief also lists the load-bearing intermediate
   facts `solve_visible` derives: origin clusters, the retraction, registry base rates,
   the non-diagnostic set; never the verdict). 60 seeds × 4 arms × 1 run, plus 3 runs on
   20 seeds to estimate run-to-run variance.
   - **G1b (the instrument works):** oracle-fed beats unaided at p < 0.01. If it doesn't,
     nothing else from P1 is read; fix the instrument.
3. **Family P on this bench.** 20 seeds × 4 information-free variants (reorder, rename,
   rephrased confidence, reformat), for the *unaided* and *v1.3-available* arms. Reports
   the verdict flip rate with a denominator (finding 5).

**What P1 answers:** *available vs unaided* is what v1.3 does as shipped. *Ordered vs
available* is what non-dependence costs. Uptake comes from traces. **What P1 does not
answer:** anything about long horizons. The bench is short, and two of its traps are
handed over (see `bench/README.md`).

   before trusting them. A first read looked like broken keys; it was wrong. The chains
   run through the club's *sport* (Alta IF → baseball, a newer fact → created in Japan, a

   The dataset's wording ("the country Alta IF originates from" means the sport's country)

   reconstruction check on every item (model proposes the fact chain, code verifies each
   cited fact exists, is the newest for its subject and relation, and links to the next)
   is **owed before these families are used confirmatorily** (D4).

   **Runner hardening, same day:** `--allowed-tools Write` could pre-approve writes outside the sandbox, so

   pre-approved. Verified with a probe: the write inside the sandbox succeeded, the write to
   `/tmp` was denied, and no shell existed. Scaffold arms get the recipes' arithmetic from
   the MCP server rather than the bundled scripts. That removes host execution, so Docker is
   no longer a prerequisite.

   **Paired pilot, 2026-09-15** (the two in-band families, 20 items each; arms: unaided a
   second time, v13-available, v13-ordered; 120 runs, 0 void, about $10 at list price on the
   subscription):

   | Family | unaided r0 / r1 | v13-available | v13-ordered |
   |---|---|---|---|
   | `gsm-ct` correct | 13 / 15 | 16 | 17 |
   | `mab-mh32k` correct | 8 / 11 | 13 | 14 |
   | skill used (from trace), `gsm-ct` | — | **0 of 20** | 20 of 20 |
   | skill used (from trace), `mab-mh32k` | — | **0 of 20** | **2 of 20** |

   Fixed and broken against unaided r0: plain rerun +3/−1 (gsm), +5/−2 (mab);
   available +4/−1, +5/−0; ordered +4/−0, +7/−1.

   What it says, plainly:
   - **The noise floor is large.** Re-running plain Haiku fixed 8 of its own 19 failures.
     Available fixed 9, ordered 11. At n = 20 none of this separates from noise.
   - **Available skills were never used** (0 of 40 runs), so any available-vs-unaided
     difference can't come from running a skill. It is noise, or priming from the skill
     descriptions sitting in context. A sham arm with the same amount of irrelevant skill text
     is the test for the second.
   - **The order to use the skill got lost in the long context.** Placed before a 34k-token
     fact list, Haiku followed it in 2 of 20 runs; placed before a short math problem, 20 of
     20. The dependence failure the brief describes, measured from outside, in exactly the
     regime the bet is about.
   - **Opus's fix predictions were worse than a coin flip.** Brier 0.33 (available) and
     0.30 (ordered), against 0.25 for always saying 0.5. It predicted a 22% fix rate for
     available while a plain rerun alone fixed 42%, because it ignored rerun noise. Future
     prediction prompts must ask for the fix rate *relative to a plain rerun*.
   - **Power:** with the observed discordance (0.2–0.35), detecting a 10-point paired
     difference at 80% power needs roughly 150–270 items per family. MemoryAgentBench has
     only 100 multi-hop questions per tier.

   |---|---|---|---|---|
   | positive control: oracle-fed vs unaided r0 (49 items) | 98% correct | — | 15 / 0, p = 0.00003 | **passed** |

   sham −2.0 (−7.1 to +3.1). Same verdicts.

   Uptake from traces: v13-available invoked a skill in **0 of 200** runs; v13-ordered in
   200 of 200 (critical-thinking every time; it went on to `ct-assumption-audit` 4 times,
   `ct-reframe` and `ct-question-tree` once each). On the 38 items plain Haiku got wrong on
   both runs, ordered fixed 11 and available 5. Cost per run: about $0.017 available and
   sham, $0.021 ordered.

   Opus's predictions (45 unaided failures, logged before any scaffold arm ran): mean
   predicted fix rates matched the outcomes (available 0.28 vs 0.29 actual; ordered 0.46 vs
   0.44), but item-level Brier was barely better than a constant at the true rate (0.19 vs
   0.21; 0.22 vs 0.25). It still underestimated plain reruns (0.12 vs 0.24). Opus can
   estimate the average; it can't tell which items the skills will fix.

   **What this says, plainly:**
   - The instrument can see an effect: the oracle arm moved 15 items with 0 broken.
   - **Skills that are merely available do nothing on this task**, because Haiku never
     opens them. Garden skills of the same size do nothing either, so skill text in the
     prompt is not a nudge in either direction.
   - **Ordering Haiku to use the controller helps, by about 8 points**, with a confidence
     interval that excludes zero but doesn't clear the pre-registered 10-point bar.
   - Not yet separated: whether that gain comes from the critical-thinking *content* or
     from *any* instruction to pause before answering. The next arm is an ordered sham
     (a generic "re-read the problem before answering" order of matched length).
   - The design consequence matches R§0: the value shows up only when something makes the
     model use the scaffold. Advice gets 0% uptake; an order gets 100% on short prompts and
     10% when placed before a long context. That points at hooks that inject at the right
     moment, not at more recipes.

   **Second subject model: Gemini 3.5 Flash Lite, 2026-09-15 — attempt invalid, sandbox
   incident.** Same harness, pointed at OpenRouter (`google/gemini-3.5-flash-lite`, every
   model slot pinned to it). A 120-run headroom probe exposed three runner defects, all
   fixed, and the Gemini runs from that day (label tag `@gemini`) are **not usable as
   measurements**:
   1. *Budget cap.* Through a gateway, Claude Code prices an unknown model as if it were
      Claude, so `--max-budget-usd` aborted 41 cheap runs. Removing the cap without a
      replacement let a retry batch run away: some Gemini runs spawned 60–76 subagents and
      hundreds of tool calls, and the retry billed **$8.73**, exhausting the OpenRouter key's
      $10 limit (total billed $10.13). Now: no Claude-priced cap for gateway runs, a
      per-batch `--max-spend-usd` read from OpenRouter's own usage, and the key's limit.
   2. *Sandbox escape.* `--allowed-tools Read Glob Grep` pre-approved those tools for **any
      path**, and `Monitor` (runs a shell command) was never disallowed. Gemini, apparently
      hunting for the GSM8K dataset, listed files under `/private/tmp`, the temp folder,
      `/opt`, `/Library` and `/usr`, read scripts other Gemini runs had written, and ran 19
      distinct harmless commands through `Monitor` (file waits, `ls`, `tail`, `echo`). A
      scan of every tool result found **no answer key, repo data file or dataset copy read**.
      Now: nothing pre-approved, `Monitor`, `NotebookEdit`, `PowerShell` disallowed; a probe
      that tried `/private/tmp`, `/Users`, `/etc/hosts` and a shell command was denied on
      each while in-sandbox read and write still worked; and any successful tool call on a
      path outside the sandbox, or any successful command tool, now voids the run.
   3. *Empty result.* Gemini sometimes ends a turn with a thinking block after its answer;
      the parser now falls back to the last top-level text.

2. **Recreate on Haiku, unaided.** 50–100 items per chosen dataset through `run_arm`,
   scored against gold by deterministic code. This measures Haiku's *actual* failure rate;
   published rates are not trusted, because public items may be memorized. A dataset
   outside the 30–85% band on Haiku is dropped for that reason, and the drop is reported.
3. **Run every arm on every item, before looking at who failed.** Unaided runs a second
   time as its own control, next to v1.3-available and v1.3-ordered. **Never rerun only the
   failures:** a run-to-run coin flip turns some failures into passes on any rerun, so
   failure-only reruns show a fake improvement (regression to the mean).
4. **Opus 5 assesses, blind.** For each unaided failure it codes the error class (E1–E5,
   R§2.1) and writes a probability that a scaffold would fix it, **logged and hashed before
   the scaffold arms are scored**. Rules:
   - Opus sees the task, the gold and a plain-text final answer. It never sees which arm
     produced an answer, and ledger files, cards and skill names are stripped, so structure
     can't earn credit (D10 applies to model judges too).
   - Where a deterministic gold key exists, the key scores the item and Opus does not.
     Opus scores only fields without a key, and its agreement with the key is measured on
     items that have one.
   - A second Opus pass with a reworded codebook gives a same-model agreement figure,
     labelled as such. It is not independent rating, and the plan doesn't pretend otherwise.
   - Opus is never inside an arm (H1 still holds).
5. **Settle the predictions.** The paired arm results resolve Opus's fix probabilities
   (Brier score). That shows whether "this framework may help" is a judgment worth trusting
   before anyone relies on it.

- **G2:** E2 plus the gate-reachable part of E3 is at least 15% of Haiku's failures. Below
  that, long-horizon ledger work stops; report the number and consider at most a
  digest-memory tool. Independently of G2, the paired arm comparison is the first measured
  answer to "does v1.3 help Haiku on real error types", and results report fixed and broken
  counts separately.

### P3 — Family L and the integrity detectors (weeks 3–7)

- **Generator:** deterministic, seeded, no model. Session 1 establishes a commitment from
  a tool result or stakeholder file. Sessions 2…k are 20–60 steps of legitimate drift work
  in a synthetic repo or dossier. The final session contains the collision or retraction
  and the scored probe. Sessions are **separate `claude -p` invocations sharing only the
  working directory** (a true session boundary), plus a variant that resumes through a
  forced compaction.
- **Scored fields** (R§2.2): contradiction with both polarities; the invalidation set,
  with misses and over-flags reported separately; a banded quantity; determinability
  (refuse *and* name the missing input).
- **`solve_visible` for Family L:** reconstructs every scored field from visible session
  files only (D4).
- **Detectors** (R§2.3, deterministic): reconstruction, the metadata leakage classifier,
  a variant sweep, the sandbox manifest diff, mutation tests on every scorer, and a
  clueless baseline.
- **Family S:** a seed range written into the pre-registration hash and never run
  before P6.

**G3:** Haiku unaided fails 30–85%; every detector passes; instance rejection stays under
50%. A family that fails two revision rounds is discarded, and the discard is reported.

### P4 — Pilot, power and pre-registration (weeks 7–8)

- 30 Family L instances × {unaided, strong-memory, v1.3-available, oracle-fed} × 3 runs,
  on Haiku.
- Estimate σ of the paired difference; compute the MDE at candidate n.
- `measure.py` emits the five R§3.3 verdicts and must recover the planted +δ, 0, −δ and
  ceremony-only bundles before it judges anything real.
- Pre-registration committed with its hash: metrics, arms, n, exclusions, stopping rules,
  δ, equivalence band, analysis code, Family S seed range.

**G4:** MDE ≤ δ at an affordable n; oracle-fed beats unaided; strong-memory closes less
than 70% of the oracle-to-unaided gap (otherwise harness memory already does the job, so
stop). **D-2 is decided here.**

### P5 — Minimal v1.4 scaffold (weeks 9–14, only if G4 passes)

Each piece is a removable unit, and each has a **sham twin** with the same files, the
same card and the same spend, but the mechanism disabled.

1. **Ledger.** Append-only JSONL under `.ct/ledger/`, hash-chained, with kinds
   `observation | computation | elicitation | prediction | gap`. `depends_on` is set at
   write time; a missing link means "depends on every live entry in the session". Pure core
   in `src/ctmcp/core/` plus a stdlib script with parity tests, extending
   `dependencies.py` and `commitlog.py`.
2. **Harvest hook** (`PostToolUse`): records tool-call id plus content hash as
   `observation` entries. The agent can't skip it.
3. **Digest hook** (`SessionStart` on startup/resume/compact): injects live commitments,
   open gaps, suspect entries and due predictions.
4. **Collision flag.** On write: entity overlap, a same-dimension quantity, or touching a
   suspect entry → the candidate pair is injected into context. No model call.
5. **Card renderer** (code) plus a `Stop`-hook annotation. It never blocks beyond the
   existing block-once-and-fail-open rule.

**Not built in P5:** the proxy, the cold reader, counterpart panels, calibration expiry,
and any contest UI beyond a CLI recompute. Each needs its own gate.

Must end green on all four repo commands, with exact-value and parity tests.

**G5:** collision-flag precision ≥ 0.5 at ≤ 1 flag per 10 writes on development instances;
the card test runs with whatever readers exist, and the result is reported as reduced.

### P6 — Confirmatory study and frontier check (weeks 15–19)

- **Haiku, Family L, n from G4** (≈ 400 expected). Arms: unaided, strong-memory, sham,
  v1.4, oracle-fed. Family P variants included. Family S scored last and reported
  separately.
- **Leave-one-out:** v1.4 minus each of units 2–4 at matched budget.
- **Frontier check:** Opus 5, and Sonnet 5 if the budget allows, on a 100-instance subset:
  unaided vs v1.4.

**G6:** `measure.py` issues the verdict. A null is **void** unless oracle-fed beat unaided
at p < 0.01 in the same run. v1.4 must beat sham.

## 8. Stop rules

1. **G1b / G4 / G6:** the positive control fails → no reading, repair the instrument.
2. **G2:** addressable error < 15% → stop the long-horizon ledger work.
3. **G3:** no family lands in the 30–85% band after two revisions → stop and report.
4. **G3:** instance rejection > 50% after detector tuning → the generator is unsound.
5. **G4:** MDE > δ at an affordable n → buy more instances or stop, never run underpowered.
6. **G4:** strong-memory closes ≥ 70% of the oracle gap → stop.
7. **P5/P6:** a unit costing > 2× baseline without a primary-metric gain is removed.
8. **G6:** v1.4 ≈ sham → no mechanism claim.
